Multi-Factor Authentication for Web Applications

A working demonstration of layered authentication: a strong password hashed with Argon2id, followed by a time-based one-time password from an authenticator application. A stolen password alone is not enough to reach a protected page.

How signing in works

  1. You enter your username and password.
  2. The server verifies the Argon2id hash.
  3. A short-lived pending state is created — not a session.
  4. You enter the 6-digit code from your authenticator app.
  5. Only then is a full session issued.
A2

Argon2id password hashing

Memory-hard hashing with a per-user salt. Plaintext passwords are never stored, logged or recoverable.

OTP

TOTP second factor

RFC 6238 codes from any standard authenticator app, with a documented clock-skew window and single-use enforcement per time step.

KEY

Secrets encrypted at rest

TOTP seeds are encrypted with a key held outside the database, so a database dump alone yields nothing usable.

RC

Single-use recovery codes

Ten hashed backup codes, each valid once, so a lost phone does not mean a lost account.

LOG

Security audit trail

Every authentication decision is recorded — without ever writing a password, OTP value or recovery code to the log.

RBA

Role-based access control

Administrator and user roles, enforced on the server for every protected operation rather than by hiding links.

Scope and honest limitations

TOTP protects against a compromised password: credential stuffing, a leaked password database, or a weak reused password. It is not phishing-resistant — a real-time phishing proxy can relay a code within its validity window. Origin-bound credentials such as WebAuthn/passkeys are the phishing-resistant answer, and are documented as future work rather than claimed here.

This is an academic demonstration system built for assessment at ISBAT University. It is not hardened for production use.
